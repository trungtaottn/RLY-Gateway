# Project Decisions

## Product identity

- Brand/product: `RLY` / `RLY Gateway`.
- Repository/package/CLI: `RLY-Gateway` / `rly-gateway` / `rly`.
- Local checkout and durable state root: `rly-gateway` / `~/.rly`.
- The first RLY start migrates a legacy `~/.agent-gateway` tree only when `~/.rly` is absent; two roots are an operator-resolved conflict.
- Development posture: private-first and public-ready.
- License: MIT, with per-module upstream provenance for copied or substantially adapted code.

## Runtime defaults

- TypeScript strict on Node.js active LTS.
- pnpm, Fastify, native fetch/Undici, Zod at external/config boundaries, Vitest.
- TOML launch configuration plus versioned SQLite control-plane metadata.
- Deterministic default loopback port `17871`.
- Persistent per-user resident runtime service first: `rly init` installs a user LaunchAgent (macOS) or `systemd --user` unit (Linux), starts the resident runtime, and `rly <profile>`/diagnostics reuse it. The foreground launcher lifecycle remains the fallback when no service is initialized. (Supersedes the earlier "foreground first, background service later" posture; see ADR 0006.)
- `rly config` is the primary user-facing control plane after `rly init`: it resolves durable configuration from the `~/.rly` installation record (no `gateway.config.toml` in the current working directory on the normal installed path), ensures/reuses the resident runtime (recovering the registered service when it is down and falling back to a session-scoped foreground runtime for uninitialized checkouts), opens the local loopback config UI through the existing single-use fragment bootstrap, and exposes focused provider/account/pool/profile shortcuts over the same management API and policy revision as `rly admin`. `rly init` remains one-time machine/user bootstrap; provider add/re-auth happens from `rly config`.
- macOS LaunchAgent specifics (#33): one stable per-user label `com.rly.gateway` in the current user's `gui/<uid>` launchd domain; `~/Library/LaunchAgents` plist at mode `0600`; normal `rly init` never requires root and refuses to run as root; service stdout/stderr land in the durable RLY log directory (`~/.rly/logs/service.log`); the plist holds absolute executable/state paths only and contains no credentials, tokens, or account identity; crash restart is bounded by an explicit launchd `ThrottleInterval` so repeated broken startups are diagnosable rather than a tight loop; changed/stale definitions are unloaded before reload during init/update; launchctl v2 and legacy subcommands are both tolerated; service registration/load state and pid are reported separately from runtime `/identity` readiness.
- Linux `systemd --user` specifics (#34): one stable per-user unit `rly-gateway.service` under `~/.config/systemd/user` at mode `0600` (directory `0700`); normal `rly init` never requires root and refuses to run as root; the unit uses absolute executable/entrypoint/config paths plus the durable `~/.rly` working directory and appends service stdout/stderr to the durable RLY log directory (`~/.rly/logs/service.log`, journal default otherwise); the unit holds paths only and never credentials, tokens, or account identity, and never uses `Environment=`; crash restart is `Restart=on-failure` with explicit `RestartSec` and a bounded `StartLimitIntervalSec`/`StartLimitBurst` policy so repeated broken startups become a diagnosable `failed` state rather than a tight loop; a reachable user systemd manager (user D-Bus) is required and probed before any mutating operation — sessions without one (containers/minimal distros/WSL variants) fail actionably, and RLY never auto-enables `loginctl enable-linger` because that changes OS account behavior beyond the login lifetime; `daemon-reload` runs only when the definition changed and re-running init repairs stale definitions without duplicate units; unit enabled/active/process state is reported separately from runtime `/identity` readiness.

## Security and privacy

- Direct API credentials may use approved references. Project-owned OAuth credentials use a `0700` store with `0600` atomic files or an approved OS secret backend.
- Credential broker owns explicit import/login/refresh, single-flight, generation CAS, backup, and recovery.
- Managed bridges remain supported where they are more stable than project-owned OAuth.
- Diagnostics may include request ID, route/provider/model identifiers, capability/readiness state, timing, status, and version metadata.
- Diagnostics exclude prompts, responses, credentials, authorization headers, email, and account identity.

## Claude configuration overlay (#74) → profile-scoped Claude views (#126)

- The historical throwaway `CLAUDE_CONFIG_DIR` temp directory (which proved RLY never mutates global Claude files but also threw away user settings/agents/plugins and all RLY session history) is replaced by a **durable RLY-owned Claude configuration namespace**: `0700` directories and `0600` atomic files.
- **Asymmetric ownership is the invariant**: native Claude config (`~/.claude` or the parent `CLAUDE_CONFIG_DIR`) is read/compose-only INPUT; RLY gateway/model state is written only inside the RLY namespace. RLY never overwrites native `settings.json` (model key included), credentials, plugin metadata, history, or agent files as part of launch/exit — including any “save old global model, rewrite it back” logic (unsafe under concurrent sessions).
- **Profile scoping (#126)**: the single shared `<control-plane>/claude` namespace is replaced by deterministic per-profile/per-policy views at `<control-plane>/claude/views/<view-id>` (`deriveClaudeViewId(profileId)`, reserved `default` for profile-less launches). A profile's RLY-only model/default/cache/history state never silently becomes another profile's state; plain non-RLY Claude reads native config only.
- Composition is a typed allowlist pinned to the supported Claude Code baseline (currently `2.1.229` through #24): `settings.json` one-way merge (gateway-conflict `env` keys stripped; unsupported credential-bearing shapes such as `oauthAccounts` never composed; unrelated settings and the native `model` stay user input; a persisted RLY-only `claude-rly-*` projection model is RLY-owned state and wins on re-compose), user `agents/*.md`, `commands/*.md`, and `skills/**` one-way refresh copies, and `plugins/config.json` enablement declaration only (`enabledPlugins`/`marketplaces`; `oauthAccounts`/token-like keys and plugin cache/repos are never copied — plugin runtime state stays native, a documented difference). Unknown files, `history`, `projects`, `shell-snapshots`, `todos`, `statsig`, and `version` are never copied. `~/.claude.json` (home level) and project-local `.claude` are never touched.
- **Typed ownership and precedence (#126)**: relevant Claude/gateway/model settings classify as RLY-owned / conflicting / safe pass-through / unsupported / explicit user override, with deterministic precedence (child-only RLY gateway contract env > RLY-owned persisted projection model > explicit RLY/profile launch-policy settings > user native settings/env > client persistence in the view > defaults). A conflicting native gateway/auth/model setting never overrides RLY's scoped launch contract silently.
- **Ownership manifest and deletion reconciliation (#126)**: each view carries `.rly-manifest.json` (metadata + sha256 hashes only) classifying surfaces as native-imported / RLY-generated / view-owned. Deleted/renamed native imports are removed from the view on the next prepare only when the view copy still matches the imported hash; divergent copies are reclassified view-owned and kept. RLY never deletes a file it does not own as an import; the previous additive-only ghost-file behavior is removed.
- Refresh is deterministic and race-safe (#74, extended by #126): a file composes when missing or when native is newer under documented precedence — ownership wins over naive newer-mtime copy; unchanged native input is not rewritten, so sibling RLY sessions' `/model` writes into the same view survive; malformed native JSON surfaces are skipped, never rewritten or failed over. RLY's own writes are atomic (temp + rename); the manifest read-modify-write and reconciliation are serialized per view with a bounded reconcile lock (best-effort when busy), so concurrent RLY launches converge without corrupting views or native config.
- RLY gateway URL/token/model projection state is child-env only (`ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`) and is never persisted into view settings/history; no RLY launch/management/provider credential secret enters a view or manifest.
- RLY session/history state under a view is durable across RLY launches instead of being deleted at every child exit.
- **Migration (#126)**: the legacy shared overlay migrates into `views/default` deterministically (crash-safe two-phase sibling rename), never modifying native `~/.claude`; ambiguous shared persisted state stays in the unprofiled `default` view and is surfaced, never silently assigned to a profile.
- The rule against permanent global Claude/Codex configuration mutation is **retained** and now has an explicit overlay-based mechanism behind it.
- `rly status`/`rly doctor` report per-view paths/version/composition status plus ownership/reconciliation status and conflicting key categories only; no settings, agent prompts, plugin content, session transcripts, or credentials.

## Model tiers

- Logical tiers (`haiku`/`sonnet`/`opus`/`fable`) are portable model classes resolved **inside the current execution context**: access provider first, then the parent model's model family when that provider exposes multiple families, then trusted capability evidence (#69). `fable` is never a hardcoded global alias for one vendor/model and never "the strongest model across all authenticated providers".
- Tiers are not upstream model ids: an exact physical model request keeps the exact #68 path. Tiers resolve only to eligible trusted models under the current provider/family by default; cross-family and cross-provider fallback are explicit, trace-visible policies that are disabled by default.
- Effective tier mappings are stable for an active session/policy revision: the built-in reviewed mapping and per-profile overrides are immutable per revision, and catalog refresh (#23) proposes better mappings without silently changing trusted tier mappings.
- Existing `primary`/`fast`/`reasoning` profile roles remain unchanged; tier resolution is a parallel path for portable tier aliases (`model: fable`), and `profile.modelRoles` additionally accepts tier keys as per-profile user overrides (validated fail-closed through #68 exact evidence).

## Model intent and selector namespaces (#125)

- The incoming model selector is classified into one typed `ModelIntent` (`EXACT_PROJECTION`, `RLY_LOGICAL_TIER`, `CLIENT_NATIVE_ALIAS`, `EXACT_CLIENT_MODEL`, `INHERIT`, `DEFAULT`) before any routing, with exact source-selector provenance preserved for diagnostics. Core invariant: **`fable != rly-tier:fable`** — the client-native alias vocabulary (owned by Claude/Codex) is a different namespace from RLY's logical selector namespace.
- RLY logical tiers are addressed only through the explicit `rly-tier:<tier>` namespace; a selector claiming the namespace with an unknown value fails closed (`unknown-namespace`) and is never silently reinterpreted as an alias/exact model. Bare tier strings are never RLY policy selectors by string equality.
- Bare client-native aliases keep working for existing agent/skill files (`model: fable`) without rewriting them to physical provider model ids: they map to the equivalent RLY tier through the explicit, traceable client-alias contract, then the #69 provider/family resolver runs unchanged. The classification is deliberate and visible in the route trace (`kind`/`source`), never string equality.
- The #69 tier resolver is invoked **only** for an explicitly typed tier intent — never through accidental string matching. Exact projected selection (#72) remains exact and is dispatched before profile resolution; persisted exact model ids keep the exact #68 path and are never reinterpreted as tiers.
- Precedence is deterministic and documented (explicit `rly-tier:` → projection → client alias → inherit → default → exact model); conflicting selector sources and namespace errors have a typed failure taxonomy mapped onto the existing profile error contract. Diagnostics expose selector kind/source/resolved target only — never prompts, credentials, account identity, or settings contents.

## Native protocol rails and fidelity envelope (#119)

- RLY is a protocol-preserving gateway first and a model router second. Same-protocol traffic keeps the native encoder/decoder wire shapes as the source of wire truth; RLY patches only RLY-owned controls (selected model/auth/endpoint). The semantic core (`CanonicalRequest`/`CanonicalEvent`) stays the routing/capability/tool/reasoning/diagnostics projection and never becomes the only source of truth for provider/client-owned opaque continuation state.
- A versioned **fidelity envelope** (`src/core/fidelity.ts`, version 1) carries typed opaque continuation artifacts (kind, stable item/block association, value), translation provenance (`preserved-native`/`translated`/`ignored`/`unsupported`), and the artifact kinds a compatibility claim requires. Adapters/protocol codecs may preserve opaque artifacts; routing policy inspects only explicitly modeled safe metadata (kind, association, disposition), never artifact values.
- Anthropic thinking `signature` (and streaming `signature_delta`, ordered relative to thinking/content events) is preserved natively into the envelope and onto the aggregate thinking block; a required signature on a path that cannot represent it fails closed (`unsupported-fidelity`) — nothing is fabricated, decrypted, or silently dropped.
- OpenAI Responses reasoning item identity is semantic (non-secret) and opaque `encrypted_content` is an envelope artifact retained with the exact item association across decode → continuation storage → subsequent `previous_response_id` request construction → re-encode; opaque content is never reconstructed from summary text.
- Unknown additive native fields are recorded as intentionally ignored with provenance, not silently treated as required continuation state. Opaque artifact kinds stay a typed extension point (Gemini/OpenRouter/DeepSeek) so canonical routing does not need redesign for future provider-owned artifacts.
- Opaque artifact values are runtime/protocol state, never diagnostics: they are never logged, never in route traces, never in diagnostic bundles, and are redacted by the observability redactor; `describeFidelity()` exposes provenance metadata only. Continuation persistence applies the existing private-file/storage rules.

## Subagent model resolution (#71)

- Claude Code orchestrates agents; RLY resolves their requested execution target and reasoning safely. RLY never inspects prompts to infer task type and never becomes a workflow engine — it responds only to explicit agent/tier/effort signals (`X-Claude-Code-Session-Id`, `X-Claude-Code-Agent-Id`, `X-Claude-Code-Parent-Agent-Id` and the portable `model: fable`/effort request).
- A subagent's tier resolves inside its parent agent's execution context: the session-scoped, lease-bound registry records each agent's frozen physical model/family after successful resolution, and the subagent inherits that context (exact parent match → session main context → unambiguous launch-session profile default). No global strongest-model search and no cross-provider/family substitution: an undeterminable family fails closed (`family-unknown` → `tier-unavailable`).
- The parent/main session's model, profile mapping, and global Claude settings are never mutated by subagent execution; concurrent subagents with different agent ids resolve independently under one launch session.
- No global `CLAUDE_CODE_SUBAGENT_MODEL` override exists; the source agent/skill definition (`model: fable`) is never rewritten to a physical model. The supported client baseline's native `fable` alias behavior is classified by #24 canaries.
- Agent attribution is runtime data, not authorization; launch/gateway tokens keep the security boundary. Traces carry only hashed agent linkage pseudonyms; credentials, prompts, and durable user identity never enter diagnostics.

## Gateway model discovery and projection (#72)

- RLY exposes the configured, trusted model universe to Claude Code through authenticated `GET /v1/models` on the gateway listener using the supported Anthropic Messages discovery wire contract. Discovery is a **presentation + exact-target selection surface**: #67 remains canonical evidence, #69 remains contextual tier resolution, #23 refresh stays propose-only and never mutates projections, and the account selector remains the account/credential authority.
- Every discoverable id uses the Claude-compatible `claude-rly-...` namespace (the supported client only adds ids beginning with `claude`/`anthropic`). Ids are transport/user-selection handles only; an explicit reverse mapping resolves each id to one exact access-provider/model target and provider pool, and routing never parses id strings or derives security decisions from them.
- A model is discoverable only when its access provider is enabled in the active policy, the session has an explicit provider→pool route for that provider (the profile's own pool, or a single eligible default pool per provider — RLY never picks an arbitrary pool), the model has trusted registry evidence, and compatibility is `VERIFIED` by default (`EXPERIMENTAL` requires the explicit `gateway.modelDiscovery.experimentalModels` config opt-in; `BROKEN`/unreviewed never).
- The same upstream model through two access providers appears as two distinct selectable targets (distinct ids/display labels) because auth/pool/endpoint/terms are different execution paths.
- Each launch session pins its model-universe snapshot (policy revision/hash, registry revision, provider→pool bindings, experimental policy) at issue time; a registry/policy change during an active session never silently remaps an already-issued projection id, and removed/broken targets fail explicitly rather than substitute another model.
- An RLY-only projection selected via `/model` persists only inside the RLY overlay; `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` is child-env only, and a plain `claude` launch never inherits RLY discovery env, auth, or projection ids (see Claude configuration overlay above).

## Safe zero-downtime runtime update (#73 / #92 / #93)

- Installation and activation are deliberately separate durable states: `rly update` may install a verified candidate while the old resident runtime keeps serving existing Claude Code sessions; an installed candidate is never considered active until the restarted runtime passes authenticated identity/readiness/state-open verification. Installing a candidate updates only the `staged` reference and never changes the serving `active` reference (INSTALL != ACTIVATE).
- Deployments are immutable and content-addressed: `<control-plane>/runtime/versions/<artifactId>` where `artifactId` is a SHA-256 over the exact candidate bytes/build tree, so two byte-distinct candidates with the same semantic version never share or alias one deployment directory and reinstalling the identical artifact is an idempotent no-write (semantic version is metadata only, never the storage key). Explicit `staged`/`active`/`previous` references under `runtime/refs/` are replaced atomically (temp-create + rename + parent fsync), so readers always observe a valid old or new reference, never a gap; a deployment layout is validated before any reference exposes it.
- Legacy `runtime/current`/`previous` + `versions/<semver>` layouts migrate in place without deleting a serving known-good runtime before the new ref state is durable (bytes renamed, never removed; `migrating`/`committed` marker survives crashes); malformed legacy state fails closed with a doctor recovery path.
- The serving runtime's `/identity` reports its actual runtime version, durable state/schema version, update state, active launch-session count, and drain flag through the attested handshake; the package/CLI version on disk is never proof of what is serving.
- Activation is a DURABLE TRANSACTION (#93), not an event: a secret-free journal on the update-state record moves STAGED → DRAINING → SWITCHING → PROBATION → COMMITTING → COMMITTED (or ROLLING_BACK → COMMITTED | RECOVERY_REQUIRED), each phase durably written before the action it fences, carrying the candidate/previous immutable deployment identities and a bounded rollback-attempt counter. Crash/reboot recovery makes ONE deterministic choice from the durable phase: pre-switch phases resume, post-switch phases roll back (never guessing a candidate committed), COMMITTED promotes, and interrupted/duplicate rollback is terminal `recovery-required`. The known-good `previous` reference is written before the `active` switch so it is never lost, and recovery re-establishes refs from journal evidence idempotently.
- The new-launch fence is established BEFORE the serving ref switch (#93): once activation begins, the old generation refuses new launch-session issuance while existing sessions complete naturally; in-flight streams/tool loops are never replayed or moved to the candidate. Probation accepts the candidate only after exact runtime identity + management/data protocol + authenticated readiness + durable state/schema verification; only then does the transaction commit.
- Migration rollback safety uses compatibility classes (#93) instead of the binary `migrationForwardOnly`: `none`, `backward-compatible-expand`, and `transactional-replace` are rollback-safe by contract and pass preflight; `forward-only` blocks activation before any destructive state change. Legacy manifests map true ⇒ `forward-only`, false ⇒ `backward-compatible-expand`.
- Rollback is bounded to ONE attempt (#93): the refs are restored from durable journal evidence, the service restarts at most once, and the restored runtime is verified with the same probation checks. If the single rollback attempt fails, the transaction terminates in the explicit `recovery-required` state with an actionable `rly doctor` path — never an infinite restart loop.
- The update lock records the REAL OS process-start identity from the process-attestation subsystem (#93), never acquisition wall-clock time; a live lock owned by another RLY process is never misclassified as stale, unverifiable owners are conservatively held, and only locks whose owner identity is proven stale/dead are reclaimed.
- On activation failure RLY rolls back once to the preserved previous known-good version and verifies the rollback; if both fail it stops with a deterministic doctor message. Never loop restart/rollback; never signal a process from port occupancy alone.
- Concurrent `rly update` invocations serialize through the ownership-aware stale-reclaimable update lock; crash/reboot states (interrupted install, pending activation, interrupted activation/transaction phases, stale lock) recover deterministically.
- Deployment manifests/refs carry version/build/digest/path identifiers only — never credentials, auth headers, account identity, prompts, responses, or reasoning text.
- Distribution/signing is #35 (BACKLOG): #73 owns the lifecycle once a candidate is obtained/verified; update state, artifacts, and logs are secret-free (versions/timestamps only, never credentials, tokens, prompts, responses, or account identity).

## Stable runtime bootstrap and exact build attestation (#94)

- The installed execution identity is the RLY-owned stable bootstrap, never `dist/cli/init.js` or an incidental Node path: `rly init` installs ONE launcher at `<control-plane>/bootstrap/rly-gateway` (self-locating POSIX sh, `0700` dir / `0755` script) and the registered plist/unit ExecStart references ONLY the bootstrap plus `gateway start --config <abs-config>`. The bootstrap resolves ONLY the committed #92 `active` deployment and REFUSES staged/uncommitted/missing candidates; it validates the immutable deployment and execs the real `dist/cli/main.js` dispatcher (init.js is a module, not an entrypoint). Node resolution is the bootstrap's implementation detail (RLY_NODE → PATH → recorded re-validated fallback), never part of the service definition contract.
- `rly init` establishes the INITIAL committed `active` deployment from the installed runtime tree (allowlisted package.json/dist/node_modules/LICENSE/rly.json, symlinks dereferenced for a deterministic #92 digest), idempotently — a valid committed deployment is never re-copied or rewritten. `rly update` keeps the definition on the bootstrap, so the controlled restart after the `active` ref switch boots the newly committed deployment automatically.
- Build identity is ONE versioned, secret-free object shared by `/identity`, `rly --version`, diagnostics, the release-candidate manifest, deployment metadata, and update probation: semantic version, commit/source revision, build ID, release channel (`dev`/`beta`/`stable`), control/data protocol versions, durable state/schema version, and the serving artifact digest (#92 content-addressed identity when serving from the store). Two artifacts sharing a semantic version are distinguishable by artifact digest (`sameSemanticVersionDifferentArtifact`), and an exact match requires every field equal (`exactIdentityMatch`).
- Attestation stays ONE mechanism (no parallel identity service): the ownership record's executable fingerprint is the digest of the exact serving build identity, reuse fails closed on same-semantic-version-different-artifact evidence (`attested-incompatible`), foreign/unattested listeners keep failing closed and are never signaled, and update probation requires the serving artifact digest to equal the candidate's immutable deployment identity whenever the serving runtime identifies its artifact (a same-semantic-version-different-artifact candidate rolls back; a legacy/dev runtime without an artifact identity falls back to the #73 version/protocol/readiness gate).
- Service definitions are reconciled idempotently: `rly init` and `rly doctor` detect missing/stale/path-drifted launchd/systemd definitions (rendered-content comparison) and repair them through the platform adapter; `rly status` reports read-only. Legacy definitions (Node + `dist/cli/init.js`, direct `runtime/refs/...` paths) migrate to the bootstrap contract without provider/account reconfiguration; no-root per-user semantics are preserved and unsupported platforms never falsely report registration success.
- Diagnostics may expose the bootstrap path, service-definition revision + reconciliation state, and expected/serving build identity; no credential, auth, session, or user-content data ever enters service definitions, the bootstrap script, deployment metadata, or build identity. Wave 5 owns distribution/signing; Wave 4 remains the authority for resolving the committed runtime.

## Standalone runtime artifacts are the primary production distribution (#35)

- The PRIMARY production distribution is the RLY-owned standalone runtime artifact, NOT the repository/Node development packaging: a self-contained package per supported target that installs and runs without a user-provisioned Node/npm/pnpm toolchain or a source checkout. GitHub Releases is the artifact origin; npm/Homebrew (if introduced) are secondary convenience channels that must wrap or point to the SAME canonical artifact lineage (tarball + sha256 + content-addressed digest + identity) and must never build semantically different runtime bytes under the same RLY build identity. External Node is a development concern only. This rewrites the original channel decision: standalone RLY-owned artifacts are primary; repository/npm packaging is not the runtime ownership authority.
- For MVP the exact supported Node runtime is BUNDLED (`bin/node`) and its version is pinned (`scripts/standalone/node-version.json`) and recorded in artifact build metadata (`rly-artifact.json` bundledNodeVersion + source) as the #128 SBOM input; `rly` stays the stable user-facing command while the internal layout remains RLY-owned and deterministic (`rly`, `bin/node`, `dist/`, `node_modules/`, `package.json`, `LICENSE`, `docs/third-party-notices.md`, `rly.json`, `rly-build.json`, `rly-artifact.json`). A future single-executable strategy is evaluated only after its runtime/tooling constraints are proven.
- The bundled dependency tree preserves pnpm's virtual-store layout with relative in-tree symlinks (dereferencing breaks transitive resolution — proven by `Cannot find module 'avvio'`); pnpm metadata files and `.bin` shims (which embed absolute store paths) and dependency test artifacts are pruned, and only relative in-tree symlinks are allowed (escaping/absolute links fail packaging).
- Artifact production consumes the #94 exact build identity and the canonical version authority (`RLY_RELEASE_VERSION` → exact git tag → `package.json`), resolving the `package.json` `0.1.0` vs release-tag ambiguity: a build whose `dist/rly-build.json` semantic version diverges from the resolved release version FAILS. The artifact digest is content-addressed over the exact tree (same rules as the #92 immutable store) so two byte-distinct artifacts cannot claim the same identity.
- The positive allowlist is enforced by an automated gate (unexpected files fail packaging) and absence/secret scans (credentials, `.env`, local `~/.rly` state, Git history, private reports, snapshots, and unrelated workspace files are proven absent); builds are reproducible (deterministic file lists, fixed source-date-epoch mtimes, no owner/absolute paths/store paths; identical inputs => byte-identical tarballs).
- The platform matrix is explicit per target (`supported` = built AND smoke-tested on a qualified runner; `experimental` = built deterministically, smoke-testing requires an unprovisioned runner) and no target silently reuses another target's artifact or Node bytes. Release signing/SBOM/provenance/qualification (#128) is delivered by the release supply chain decision below; installer/updater UX (#129) remains a separate track.

## Release supply chain, signing, and exact-byte qualification (#128)

- **Exact-byte qualification is the publication authority.** A release is promoted only on evidence produced by installing and exercising the EXACT artifact digest that is subsequently published — never a rebuilt equivalent, never a version label. The qualification matrix covers clean install, `rly --version`/build identity, permissions, platform signing, runtime readiness, update handoff contract, `rly init`/service registration, and uninstall; a gate is `passed` only when it executed against the exact bytes, `skipped`/`not-run` is never passing evidence, and a target without qualification evidence is NOT stable-qualified.
- **Metadata is separated from artifacts (TUF-style).** The canonical release manifest (`rly-release.json`), per-artifact SBOMs, provenance, qualification, and signed channel metadata are SIBLING release assets referencing the exact artifact digest — never embedded in the artifact (embedding would change the digest it describes). The updater verifies the signed metadata and never trusts a mutable GitHub `latest` target alone.
- **Canonical release manifest** (`scripts/release/manifest.mjs`) binds product version, channel, source commit, build ID, every supported target, artifact filename/size/sha256/content-addressed digest, bundled runtime version, state/protocol compatibility, and required signatures/attestations — consistent with the #94 exact build identity (a split identity fails publish/verify).
- **SBOM + provenance per artifact** (`scripts/release/sbom.mjs`, `scripts/release/provenance.mjs`): the SBOM is generated from the ACTUAL packaged bytes (RLY components, bundled pinned Node, third-party `node_modules` packages; deterministic, SPDX-2.3-style) and references the exact digest; provenance ties every artifact digest to the exact source revision + release workflow/toolchain inputs.
- **Platform authenticity.** macOS production artifacts must pass the documented code-signing/notarization/stapling verification gate before stable promotion; Linux uses the per-artifact Ed25519 signature + release manifest trust chain. A missing required platform signature BLOCKS promotion for that target.
- **Signed channel metadata** (`scripts/release/channel.mjs`) maps beta/stable to exact release/build/artifact digests with explicit rollback (monotonic `version` counter — lower-than-observed is refused), staleness (`updatedAt` + `maxAgeDays` — stale is refused), and freeze (explicit marker blocks activation beyond the frozen snapshot) semantics.
- **Signing key discipline.** Release signing uses Ed25519; the PRIVATE key is ONLY the repository secret `RLY_RELEASE_SIGNING_KEY` (never committed, referenced by env in the release workflow), the PUBLIC key is committed (`scripts/release/signing-public-key.pem`), and every verifier checks the signature + key fingerprint.
- **Release immutability** (`scripts/release/immutability.mjs`): published bytes/digests are never silently replaced under the same release identity — republishing the same version with different digests fails and byte replacement of published assets is detected against the signed metadata.
- **Workflow hardening.** Release-critical third-party GitHub Actions are pinned to reviewed immutable commit SHAs; release workflows use least-required `GITHUB_TOKEN`/release permissions and never configure npm credentials (npm is not the primary channel). `scripts/check-release-supply-chain.mjs` enforces these statically as part of the release gate.
- **Beta vs stable gates are machine-readable.** Beta may permit documented experimental qualification gaps (recorded as `experimental-gaps` in the qualification document and channel metadata); stable requires `qualified` status for every advertised target plus all authenticity/compatibility/privacy/Wave-4-integration gates. Beta evidence can never masquerade as stable qualification.
- **Privacy/public boundary.** Manifests, SBOMs, provenance, channel metadata, signatures, and qualification records contain public build metadata only — never credentials, tokens, local state, private source-history content, prompts, responses, or account identity.

## Runtime compatibility canary (#24 / BL-043)

- The canary is the runtime compatibility evidence gate: it reports exact installed client versions separately from binary `found` state (`src/targets/versions.ts`; version parsed from `--version` output only, never inferred from timestamps/paths), pins the supported baseline's wire contract with redacted fixtures, runs a deterministic fake gate matrix per exact access path, and classifies each path `EXPERIMENTAL`/`BROKEN`/`unknown` (since #122, a Layer A observation can never be `VERIFIED`). A newly installed unknown client version produces a visible `unknown/not-tested` status and does not silently replace the tested baseline; binary presence is never compatibility.
- The pinned fixture baseline is `claude-code-2.1.229`. The observed local client `2.1.231` and Codex `0.147.0-alpha.6.5` are recorded as observed and are not tested baselines until the corresponding evidence gate passes.
- `VERIFIED` is unreachable from any canary observation (#122): `livePassed`/`liveEvidence` are removed, a full deterministic Layer A pass classifies `EXPERIMENTAL` with `production-claim-not-established`, and production trust requires Layer B (installed client) / Layer C (live access path) evidence plus reviewed promotion (#124). A failed required contract is `BROKEN`; missing/unrun evidence is `unknown` and never reported as passed.
- Evidence is keyed by exact client kind/version + access provider + adapter/integration path + physical model; the same upstream model through two access providers never shares evidence. Capability-dependent gates stay `not-run` without reviewed evidence, so tool/reasoning capabilities are never advertised stronger than proven.
- `rly canary run` emits secret-free machine-readable evidence artifacts under `<control-plane>/canary/` for #23/#67 review tooling; the canary reports evidence and drift and never mutates `directProviderRegistry`, trusted tier mappings, or `/v1/models` projection. Promotion of proposed compatibility state remains an explicit reviewed control-plane action.
- The #72 projection gate consumes canary-derived compatibility state: `VERIFIED` by default, `EXPERIMENTAL` only with the explicit `gateway.modelDiscovery.experimentalModels` opt-in, `BROKEN`/unreviewed never.
- `rly doctor` reports installed client versions, the tested baseline, and the live-gate env; canary diagnostics/artifacts carry client/provider/model ids, gate names, status, fixture revision, and redacted error categories only — never prompts, responses, reasoning text, credentials, or account identity.

## Compatibility Claim and Evidence v2 (#122)

- Compatibility is a reviewed claim over an exact execution path, not a property inherited from a model name or a generic live flag. RLY replaces the coarse `livePassed: boolean` with a versioned, feature-scoped Compatibility Claim + Evidence model (`src/canary/claim.ts`): a stable claim key includes client kind, exact client version/baseline, source protocol/revision (#119 vocabulary), adapter/integration surface, access provider, auth mode, endpoint contract, exact physical model, and feature/capability claim. Model family is classification metadata only and is never part of the key — it can never replace exact provider/model/access identity.
- Features (text, streaming, cancellation, tools incl. parallel/multi-tool continuation, reasoning, reasoning+tools, model discovery, session/subagent attribution, config-overlay, and other relied-on features) are claimed independently; passing text never implies tool/reasoning/discovery compatibility.
- Evidence layers are explicit and never collapsed into one boolean: Layer A = deterministic protocol/adapter conformance with fake/synthetic fixtures (the current canary gate matrix is reclassified as Layer A), Layer B = exact installed-client black-box behavior (built by #123), Layer C = exact real access-path live verification (built by #123). Required layers are declared per adapter and unknown adapters fail closed (A/B/C).
- No boolean can grant production trust: `livePassed`/`liveEvidence` are removed from the authoritative classification path; classification can never emit `VERIFIED` from an observation (a full deterministic pass is `EXPERIMENTAL` with `production-claim-not-established`). `RLY_LIVE_CANARY`/`liveRunnerEnabled` may enable a runner hook (#123) but can never stand in for an evidence artifact.
- Missing/skipped/unrun evidence is distinct from PASS and FAIL (`missing`/`not-run`); a deterministic Layer A pass never implies live/production trust. Promotion of a satisfied claim to trusted registry state remains an explicit reviewed control-plane action (#124, out of scope here); `CompatibilityEvidence.claimRef` (registry revision 5) links a reviewed state to its exact claim key.
- Claim/evidence documents are versioned (`schemaVersion` 1 / `evidenceSchemaVersion` 2) and persist append/audit-friendly under `<control-plane>/claims/` with deterministic lookup by exact claim identity + feature. Legacy v1 canary outputs are flagged legacy/untrusted (`legacy-v1-artifact-untrusted-for-v2-claims`) and can never silently satisfy a stronger v2 claim — a claim lookup returns `missing` until real v2 observation. Evidence artifacts never contain credentials, auth headers, account identity, prompts, real responses, or reasoning text.

## Installed-client and live access-path runners (#123)

- Layer B (installed-client black-box) is a real-binary evidence gate, never an approximation: the runner launches the ACTUAL installed Claude Code / Codex CLI binary against a controlled local fixture server (child-only env, synthetic token, throwaway config dir) and records the exact executable path + probe version separately from the reviewed supported baseline. Black-box evidence is keyed to the exact OBSERVED client version; the observed version never becomes a supported baseline by passing (version drift surveillance — new versions are tested without auto-promotion, and a changed client behavior is a typed exact gate failure keyed to that version). A missing/non-executable binary reports every gate `not-run` (`client-not-installed`), never PASS.
- Layer C (live access-path) is opt-in, feature-scoped, and credential-safe: it runs only with explicit `RLY_LIVE_CANARY=1` and an available environment credential; each feature gate (text, streaming, cancellation, tools, reasoning, effort, discovery, attribution) carries its own request and its own Evidence v2 record so text success never promotes tools/reasoning/discovery; tool continuation is proven only when the provider returns tool calls (else `not-run`/`provider-did-not-call-tool`); missing credentials, skipped runs, and unexecuted gates are `not-run` (or absent) — never `passed`, never `VERIFIED` — and live runs never silently spend quota.
- Runners are observation-only: they never mutate the trusted registry, tier mappings, `/v1/models` projection, or effective compatibility state (promotion/quarantine/enforcement is #124). Runner artifacts are secret-free: raw results under `<control-plane>/canary-runners/` (metadata only) with Evidence v2 `ref`s and additive `timingMs`.

## Effective Compatibility Registry (#124)

- The Effective Compatibility Registry is the SOLE runtime compatibility authority. Four orthogonal concepts are resolved into ONE effective answer per exact claim/feature and are NEVER collapsed into a single persisted boolean: observed evidence (#122/#123), reviewed trust decision, observed health/freshness, and enforcement. The model registry keeps owning model identity/capability evidence; this track adds the compatibility authority and does not duplicate the model catalog.
- Positive trust requires an explicit reviewed decision tied to the exact claim identity AND evidence revision. A new PASS observation never auto-promotes; when evidence is updated after a decision the claim becomes review-stale (`untrusted`, re-review required) — evidence update never silently keeps old trust. Decisions persist secret-free (reviewer/source/reason/timestamp/revision only) under `<control-plane>/compat/reviews/` with append/audit-friendly monotonic revisions.
- A strong reproducible failure can quarantine an EXACT claim/path/feature promptly. Quarantine scope is inherently narrow (exact claim key) so one provider/model/feature failure never poisons unrelated paths or features, and quarantine never deletes historical trusted evidence; explicit lift is audit-friendly.
- Freshness/staleness is defined per evidence kind/claim class: evidence goes stale on client version/baseline drift, protocol/adapter revision drift, provider endpoint/auth-mode drift, physical model fingerprint change, fixture/corpus revision drift, material RLY build change, and evidence age. A stale positive never remains silently VERIFIED.
- Default enforcement: normal execution/exposure requires effective trusted compatibility for the exact required features; quarantined/known-broken required features FAIL CLOSED with no silent fallback across provider/family/model unless an owning policy explicitly permits it. The explicit experimental override (exact-pin opt-in / `allowExperimental`) is traceable and visible in route traces/doctor and can elevate `experimental`/`stale` but NEVER `untrusted`/`missing`/`quarantined`; a hard quarantine is bypassable only through the separately documented administrative `allowQuarantineBypass` policy, and the bypass stays visible (`quarantine-bypass`).
- Runtime consumers (model selection #68, logical tier resolution #69, model projection/discovery #72, reasoning/tool eligibility, `resolve-route`) consume ECR results; static `model.compatibility.state` is no longer the final production trust authority. The gateway builds the ECR snapshot from the claim/review/quarantine stores + the pinned runtime policy (client baseline, protocol/fixture revisions, material RLY build).
- Legacy static registry compatibility states migrate under the `seed-reference-only` policy: a static `VERIFIED` row without a `claimRef` derives `experimental` at best and can never silently satisfy reviewed v2 trust; `BROKEN` stays a hard negative seed. Auditability is preserved on trust change (monotonic revisions, append-only) and evidence expiry (freshness reasons recorded).
- `rly compat` (status/review promote|reject/quarantine/lift/explain) and doctor/status explain WHY a target is trusted, stale, quarantined, experimental, or blocked — claim identity, latest decision metadata, evidence layers, health, freshness reason, quarantine reason, enforcement reason — all secret-free (never credentials, account identity, prompts, responses, or reasoning text).

## EffectiveModelDecision control plane (#127)

- The EffectiveModelDecision is the FINAL model-control output before account selection: for every supported RLY model-routing request (profile, projected, subagent, Codex) RLY produces ONE typed, secret-free decision (`src/routing/model-decision/`) that assembles the #125 typed selector intent/provenance, the frozen physical provider/model/family target + provenance (#68/#69/#71/#72), the #70 reasoning mapping, the #124 ECR compatibility reference, the #72 provider→pool binding, policy/profile/session/registry/mapping revisions, and #126 view/env-settings ownership state. It is a recorder of existing stage outputs — it does NOT create a second model registry, tier resolver, account selector, or compatibility authority.
- Deterministic precedence (highest → lowest): explicit exact selection → RLY logical tier → client-native alias/model → subagent inherit/override → profile/session policy → env/settings ownership → persisted RLY-view state → defaults. The request's explicit selection always wins; conflicts are visible and deterministic (persisted-view vs request, launch-policy pin vs request, subagent vs frozen parent context, foreign/stale projection, gateway-contract env keys) — no hidden string/env override silently wins.
- The physical provider/model/reasoning target is FROZEN in the decision BEFORE the existing pool/account `RouteSelector`; account retry/failover inside the pool can never change the physical model or selector meaning (the two-stage safety boundary is preserved and now has one explainable control-plane object).
- Subagent decisions stay isolated: explicit child intent/reasoning win inside the parent's frozen execution context, the parent/main model and execution context are never mutated, and provider/family affinity (#69/#71) is retained.
- Persisted/resumed client state is validated against the owning profile view, the current policy/registry revision, ECR state, and the session-pinned selector namespace: RLY reads persisted `claude-rly-*` state ONLY from its owning view (routing metadata, never settings content), and a stale/foreign projection resolves only through the session's pinned universe reverse mapping — another profile's persisted model never silently becomes the effective target (fail closed with an actionable reason).
- Codex model/provider control uses the same intent/decision vocabulary without forcing Claude-specific aliases/config semantics onto Codex; client-specific behavior stays gated by exact #124 compatibility evidence.
- Diagnostics (`rly route-trace` per-decision explanation + `rly doctor` model-control contract) explain the selected model and blocked alternatives/conflicts with actionable reasons (conflicting env/settings, stale projection, unsupported alias, unavailable tier, incompatible/expired evidence, profile mismatch). Decision/doctor output is allowlisted metadata only — never prompts, responses, reasoning text, credentials, auth headers, raw account identity, or full user settings content.

## Verified installer/updater/uninstaller (#129)

- **INSTALL != ACTIVATE is the hard acquisition boundary.** The installer/updater (`rly install`, `rly update --channel`, `scripts/install.sh`) may download, verify, and install a candidate, but ONLY Wave 4 (#92/#93) may switch the serving `active` reference or restart the resident service. Update acquisition reports a `VerifiedCandidate` and stops; a later plain `rly update` resumes activation. `--install-only` stages the local candidate without activating.
- **Trust comes from signed metadata, never a mutable GitHub `latest`.** Acquisition resolves the channel through the #128 signed channel metadata + signed release manifest, verifies both Ed25519 signatures against the committed release public key (embedded in the runtime; private key only as `RLY_RELEASE_SIGNING_KEY`), evaluates rollback (monotonic per-channel version vs the durable highest observed), staleness, and freeze, enforces the channel qualification gate (stable = `supported` + `qualified`; beta permits documented `experimental-gaps`), and verifies the exact artifact digest chain (sha256/size + `<tarball>.sig` digest statement + unpacked-tree content-addressed digest + `rly-build.json`/`rly.json`/`rly-artifact.json` identity) BEFORE any install/staging mutation.
- **The installed execution identity is the stable #94 bootstrap** (`~/.rly/bootstrap/rly-gateway`) for both the per-user service definition and the user-facing `rly` launcher symlink (`~/.local/bin/rly` → bootstrap); `dist/cli/init.js`, incidental Node paths, and direct `runtime/refs/...` paths are never registered. Deterministic per-platform private/user-safe install locations are documented and no-root; a foreign/unowned path is never overwritten.
- **Uninstall preserves user data by default.** `rly uninstall` removes ONLY RLY-owned service definitions + product artifacts (`bootstrap/`, `runtime/`, `installer/`, installation + update state) and preserves `~/.rly` configuration/accounts/credential state. `rly uninstall --purge --yes` is the explicit destructive removal of the whole RLY control plane and never touches native Claude/Codex configuration.
- **The bootstrap installer is minimal and fail-closed.** `scripts/install.sh` needs only curl/shasum/tar/openssl on a clean per-user macOS/Linux machine (no source checkout/npm/pnpm/user Node, no sudo); it verifies the artifact digest chain in-shell and hands the exact bytes to `rly install`, which re-verifies the full canonical-JSON signature chain before installing — unverified content is never executed/installed.
- **Installer/update records are secret-free.** `acquisition-log.json`/`observed-channels.json`/`VerifiedCandidate` carry channel/version/build/digest/platform/path/status metadata only; privacy scans cover them.
- The #128 exact-byte qualification matrix exercises the installer verification on the exact artifact lineage (`verified-install` gate); real release signatures are verified post-publish by `verify-release.mjs`.
